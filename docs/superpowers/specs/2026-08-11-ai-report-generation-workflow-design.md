# AI Transcript-to-Daily-Report Workflow Design

**Date:** 2026-08-11

**Status:** Approved

**Target application:** ConferenceFlow

## 1. Summary

ConferenceFlow will add a template-driven AI writing workflow for daily conference reports. A user creates or opens a daily-report draft, adds attended sessions from the conference calendar, attaches an existing text transcript to a session, and either writes manually or asks AI to generate a candidate draft.

AI never writes directly into the report. It produces a Chinese candidate with source evidence. The user reviews the candidate, checks transcript excerpts or timestamps, and explicitly adopts or discards it. Daily-level fields use the report's current content rather than re-reading all raw transcripts.

The first version deliberately stays small:

- one DeepSeek-backed generation endpoint;
- current template, report content, transcript, and current user's focus as context;
- two-stage evidence extraction and writing for Session generation;
- one-stage writing for daily fields;
- an in-memory candidate preview;
- no RAG, vector database, Wiki, durable AI queue, candidate history, or audit warehouse.

## 2. Existing Application Context

ConferenceFlow currently uses:

- React 18, Vite, and TypeScript on the frontend;
- Vercel Serverless Functions for APIs;
- Firebase Authentication, Firestore, and Storage;
- `apiFetch()` with Firebase bearer tokens;
- `requireMember(confId)` for approved conference membership;
- collaborative daily reports stored under `conferences/{confId}/dailyReports/{reportId}`;
- calendar sessions stored under `conferences/{confId}/sessions/{sessionId}`;
- manual report editing, presence, snapshots, preview, publishing, and export.

The current report UI has fixed fields. A separate template system will make report and Session fields dynamic. This AI feature consumes that template model through the contract in this document; migrating legacy fixed fields to the template system is outside this feature's scope.

## 3. Goals

1. Add attended sessions from the calendar to a daily-report draft.
2. Default the picker to the current user's assigned/attended sessions while permitting search across the full conference calendar.
3. Preserve calendar-provided title, time, location, speakers, and other fixed information without AI rewriting it.
4. Allow a user to paste or upload an existing `.txt`, `.md`, `.srt`, or `.vtt` transcript for a Session.
5. Save the transcript as private source material associated with that report's Session draft.
6. Allow every template field marked `ai.enabled` to be written manually or generated by AI.
7. Generate all AI-enabled Session fields together from its transcript.
8. Generate each AI-enabled daily field independently from the report's current content.
9. Include the triggering user's focus for the current conference in every generation request.
10. Produce Chinese candidates grounded in reviewable source evidence.
11. Support `rewrite` and `append` generation modes plus an optional user instruction.
12. Protect existing collaborative content from failed, stale, or conflicting AI results.

## 4. Non-Goals for the First Version

- Audio upload, speech-to-text, speaker diarization, or transcription correction.
- Automatically deciding whether a Session is ready.
- Waiting for all Sessions before daily-field generation.
- Automatic generation without an explicit button click.
- AI generation of photographs or calendar-sourced fixed fields.
- Multiple current transcripts or transcript history per report Session.
- Chunked map/reduce processing for extremely large transcripts.
- RAG, embeddings, vector search, knowledge graphs, or a persistent Wiki.
- Durable AI job queues, background recovery, fallback models, or cross-provider routing.
- Persistent candidate history, token-cost dashboards, or an AI audit warehouse.
- Editing a candidate inside the preview, complex diffs, or selecting individual Session fields to apply.
- Switching an existing report's template without an explicit migration workflow.

## 5. Product Flow

### 5.1 Create the report and add Sessions

1. The user creates or opens a daily-report draft bound to one immutable template version.
2. The Session picker opens on **My Sessions**, based on the current user's calendar assignment/attendance.
3. The user may search the entire conference schedule for temporary attendance or delegated coverage.
4. Adding a Session creates its template-driven Session draft and retains the Calendar Session reference.
5. Calendar-sourced fields are rendered as fixed information and are never part of an AI output target.

### 5.2 Add source material

Each Session draft contains a private Transcript area that does not appear in report preview, publishing, or export. The user may:

- paste text;
- upload `.txt`, `.md`, `.srt`, or `.vtt`;
- view the current transcript;
- replace it safely;
- delete it.

Manual editing remains available with or without a transcript. Session AI generation requires a transcript and explains this requirement if none is attached.

### 5.3 Generate Session content

1. The user clicks **AI Generate Session Content**.
2. The UI offers:
   - **Rewrite and improve:** generate complete replacement values;
   - **Add missing content:** generate only new, non-duplicative content;
   - an optional instruction, such as “highlight deployment cost” or “limit to three bullets.”
3. The dialog displays the current user's conference focus that will be used.
4. The server extracts grounded evidence from the transcript.
5. The server generates candidate values for every AI-enabled Session field defined by the current template.
6. The UI displays one candidate grouped by template field, with expandable evidence.
7. The user chooses **Adopt**, **Regenerate**, or **Cancel**.
8. Adopting applies all successfully generated Session fields. Fields reported as insufficient remain unchanged.
9. The user may continue manually editing the adopted content.

### 5.4 Generate a daily field

1. Every AI-enabled daily field has its own **AI Generate** button.
2. The user chooses the same generation mode and may add an instruction.
3. Generation may be triggered at any time. There is no Session readiness check.
4. The server reads the report's current Session and daily content, the target field's existing content, its template definition, and the triggering user's focus.
5. The server does not re-read every raw transcript for a daily-field request.
6. The candidate cites the report fields and Sessions that support it.
7. Adoption changes only the target daily field.

## 6. Template Contract

Templates are versioned and immutable after publication. A report binds to `templateId`, `templateVersion`, and `templateHash` when it is created. Later template edits create another version and do not change existing reports.

The minimum AI-facing field contract is:

```ts
type TemplateFieldType =
  | "rich_text"
  | "bullet_list"
  | "short_text"
  | "image"
  | "fixed";

type AiSource =
  | "transcript"
  | "current_draft"
  | "calendar"
  | "user_focus"
  | "report_content";

interface TemplateField {
  id: string;
  label: string;
  description: string;
  type: TemplateFieldType;
  scope: "session" | "daily";
  ai: {
    enabled: boolean;
    instruction?: string;
    allowedSources: AiSource[];
    evidenceRequired: boolean;
    allowedModes: Array<"rewrite" | "append">;
    minItems?: number;
    maxItems?: number;
    maxLength?: number;
  };
}
```

`description` explains the field to both the user and the model. `ai.instruction` contains enforceable writing guidance such as output length, item count, emphasis, and prohibited behavior. Structured source, evidence, type, and length policies must not be encoded only in natural-language descriptions.

The server, not the browser, loads the bound template version and derives valid generation targets. Model output is keyed by stable `fieldId`, never by translated display labels.

For the initial report templates, every non-image, non-fixed content field uses `ai.enabled: true`, matching the requirement that all editable report text can be AI-assisted. Photos and fixed fields use `ai.enabled: false`. The flag remains explicit in the contract so a future template may intentionally define a manual-only field. A field that does not support appending omits `append` from `allowedModes`.

## 7. Minimal Data Additions

### 7.1 Per-conference user focus

Add one optional text field to the existing member document:

```ts
interface Member {
  aiFocus?: string;
}
```

Path:

```text
conferences/{confId}/members/{uid}
```

The focus may contain prose or newline-separated directions. Every request uses only the triggering user's focus for the current conference. It is never aggregated with other members' focus. It may influence selection, emphasis, and implications, but cannot create or override facts.

### 7.2 Report template reference

Each report stores:

```ts
interface ReportTemplateRef {
  templateId: string;
  templateVersion: number;
  templateHash: string;
}
```

Template versions are retained under the template system's immutable version collection:

```text
reportTemplates/{templateId}/versions/{version}
```

### 7.3 Current Session transcript reference

Each report Session draft stores at most one current transcript reference:

```ts
interface TranscriptRef {
  storagePath: string;
  fileName: string;
  format: "txt" | "md" | "srt" | "vtt";
  contentHash: string;
  uploadedBy: string;
  uploadedAt: number;
}
```

Storage path:

```text
conference-transcripts/{confId}/{reportId}/{sessionId}/{fileId}.{ext}
```

Raw transcript content and extracted evidence are not embedded in the main report document. The MVP does not persist normalized segments, evidence sets, or candidates.

### 7.4 Candidate state

The candidate exists only in React modal state. It is lost on navigation or refresh. This is intentional for the MVP. Only adopted field values enter Firestore.

## 8. Transcript Upload and Replacement

1. Validate the extension and text encoding in the browser before upload.
2. Paste input is converted to UTF-8 plain text.
3. Upload the new source to the conference-scoped Firebase Storage path.
4. Store its `TranscriptRef` only after upload succeeds.
5. When replacing, keep the previous reference until the new upload and Firestore update both succeed.
6. After the new reference is committed, delete the old Storage object on a best-effort basis.
7. Reject empty text and normalized content longer than 500,000 Unicode code points. Chunked processing is deferred rather than silently truncating input.

The current general Storage rule permits every authenticated user to access non-public objects. A specific `conference-transcripts/{confId}/...` rule must instead require an approved member of that conference. Public report viewers must never receive transcript access.

## 9. AI API Contract

Logical endpoint:

```text
POST /api/conferences/{confId}/reports/{reportId}/ai/generate
```

Request:

```ts
type GenerateRequest =
  | {
      scope: "session";
      sessionId: string;
      mode: "rewrite" | "append";
      instruction?: string;
    }
  | {
      scope: "daily";
      targetFieldId: string;
      mode: "rewrite" | "append";
      instruction?: string;
    };
```

For Session requests, the server derives all AI-enabled Session fields from the template. The client cannot select hidden or fixed fields. For daily requests, the server verifies that `targetFieldId` is an AI-enabled daily field and supports the requested mode.

In Session `rewrite` mode, the server targets every AI-enabled Session field. In Session `append` mode, it targets only AI-enabled fields whose `allowedModes` include `append`; other fields remain unchanged and are not treated as insufficient.

Response:

```ts
interface GenerateResponse {
  candidate: Array<{
    fieldId: string;
    value: unknown;
    evidenceIds: string[];
  }>;
  insufficientFieldIds: string[];
  evidence: Array<{
    id: string;
    sourceType: "transcript" | "report_field" | "current_draft";
    sourceId: string;
    quote: string;
    startMs?: number;
    endMs?: number;
  }>;
  context: {
    templateHash: string;
    transcriptHash?: string;
    baseFieldHashes: Record<string, string>;
    focusUsed: string;
  };
}
```

No response data is written automatically. The DeepSeek API key is available only through a server environment variable.

## 10. Server-Side Context Assembly

After `requireMember(confId)` succeeds, the server loads authoritative data rather than accepting it from the browser:

1. the daily report and its bound template version;
2. the target Session or daily field;
3. current report field values;
4. the triggering member's `aiFocus`;
5. Calendar Session metadata where allowed by the template;
6. the report Session's current `transcriptRef` for Session generation;
7. the requested mode and optional instruction.

Before starting, the frontend flushes pending debounced saves. The server computes hashes of target field values and returns them with the candidate. Focus and optional instructions may influence emphasis but are lower priority than system grounding rules and template constraints.

Transcript and report source text are explicitly delimited as untrusted data. Instructions found inside them, such as “ignore previous instructions,” are never treated as model instructions.

## 11. Session Evidence and Writing Pipeline

The Session path makes two sequential `deepseek-v4-flash` JSON-output calls inside one server request.

### 11.1 Deterministic parsing

No model is used for parsing:

- `.srt` and `.vtt` become ordered segments with stable IDs, text, start time, and end time;
- `.txt`, `.md`, and pasted text become ordered paragraph segments with stable IDs and source positions;
- whitespace is normalized for comparison while original text remains available for display;
- the complete supported-size segment list is passed to one Evidence call in the MVP.

Example segment:

```json
{
  "segmentId": "seg_0042",
  "startMs": 723000,
  "endMs": 730000,
  "text": "在同样精度下，推理成本降低约 30%。"
}
```

### 11.2 Evidence call

The first model call receives the delimited transcript segments and relevant field descriptions. It returns facts or supported synthesis items:

```json
{
  "facts": [
    {
      "claim": "该方案在同等精度下降低约 30% 的推理成本",
      "kind": "explicit",
      "segmentIds": ["seg_0042"],
      "quotes": ["在同样精度下，推理成本降低约 30%。"],
      "fieldHints": ["key_takeaways"]
    }
  ]
}
```

The server then verifies:

- every segment ID belongs to the current transcript;
- every quoted passage exists in the referenced normalized text;
- evidence required by a claim is present;
- obviously cited names, dates, and numbers occur in the referenced passage.

Invalid facts are removed. If no usable evidence remains, writing is not attempted for evidence-required fields.

### 11.3 Writing call

The second call receives:

- validated Evidence;
- current Session draft values represented as labeled `current_draft` source blocks;
- fixed Calendar metadata allowed by the template;
- current user's focus;
- target field definitions and instructions;
- generation mode and optional instruction.

It returns structured Chinese values by `fieldId` with Evidence references. The server validates field IDs, types, item counts, lengths, source policies, and Evidence references. Invalid or unsupported fields are placed in `insufficientFieldIds` and retain their current values.

The model may use current manually written Draft content when the template permits `current_draft`. Any candidate statement relying on it cites an exact Draft excerpt with `sourceType: "current_draft"`; it is never mislabeled as transcript evidence.

`explicit` content states directly supported facts. `synthesis` content, including implications or recommendations, must cite the supporting facts even when its exact wording does not appear in the transcript. The UI remains the final semantic-review gate.

## 12. Daily-Field Writing Pipeline

Daily generation uses one DeepSeek call:

1. Convert the current report content into stable, labeled source blocks such as `session:S204:key_takeaways`.
2. Include the target daily field's template description, AI instruction, existing value, current user's focus, generation mode, and optional instruction.
3. Ask DeepSeek for the target field value plus source-block IDs and exact supporting excerpts.
4. Validate source-block IDs, excerpts, type, length, and template rules.
5. Return a candidate for only the target field.

Daily fields may include core points, onsite intelligence, community voices, deep analysis, or any future AI-enabled field defined by the template. If current report content cannot support a field, the server returns it as insufficient instead of reading raw transcripts or inventing content.

## 13. Generation Modes

### Rewrite and improve

- The model reads the current value and sources.
- It returns a complete new value.
- Adoption replaces the target field.

### Add missing content

- The model reads the current value and sources.
- It returns only information not already covered.
- Adoption appends according to field type: new list items for `bullet_list`, or a separated paragraph for `rich_text`.
- The option is shown only when the template field supports `append`.
- For Session-wide generation, fields that do not support `append` are skipped and remain unchanged.

In both modes, the optional user instruction cannot override grounding, source, language, or template constraints.

## 14. Candidate Preview UI

### Session draft

- Calendar metadata remains at the top.
- A Transcript row provides paste/upload, view, replace, and delete actions.
- Manual template fields remain editable.
- One **AI Generate Session Content** button opens the generation setup.

### Generation setup

- Mode selector: Rewrite and improve / Add missing content.
- Optional instruction text area.
- Read-only display of the current user's focus used in this request.
- Generate and Cancel actions.

### Candidate result

- Group generated values by template field.
- Each field may expand its transcript or report-source evidence.
- SRT/VTT evidence displays timestamp ranges; plain text displays source excerpts.
- Show insufficient fields without clearing their current content.
- Actions: Adopt this candidate, Regenerate, Cancel.

Session adoption applies all successfully generated fields. The MVP does not allow candidate editing or per-field selection inside the modal. Adopted content remains manually editable in the report.

## 15. Collaborative Conflict Handling

The MVP uses a lightweight optimistic check rather than a new Apply service:

1. The response includes hashes of every target field as they existed during generation.
2. Before adoption, the UI compares those hashes with the latest values received by the existing Firestore subscription.
3. If any target field changed, adoption is blocked and the user is asked to regenerate.
4. If the current transcript hash differs from the response, a Session candidate is stale and cannot be adopted.
5. If values are unchanged, the existing `saveField` or `saveSessionField` paths write the candidate.

The check is intentionally conservative. The MVP does not attempt an automatic merge.

## 16. Error Handling

AI failure must never mutate report content.

| Failure | Behavior |
|---|---|
| Empty, unsupported, or undecodable transcript | Reject before replacing the existing transcript |
| Missing Session transcript | Explain that a transcript is required; manual editing remains available |
| Invalid SRT/VTT | Return a format error before calling DeepSeek |
| DeepSeek timeout, rate limit, or transient server error | Retry once, then return a retryable UI error |
| Empty or invalid JSON | Retry once, then fail; never parse free-form output as a fallback |
| Invalid Evidence reference or quote | Remove the item; never display it as normally grounded content |
| Insufficient material for a field | Leave the current field unchanged and identify it as insufficient |
| Transcript replaced while generating | Discard the stale candidate |
| Draft changed while generating | Block adoption and request regeneration |
| Template hash mismatch | Reject the result and reload the report's bound template |
| User cancellation | Abort the browser request on a best-effort basis and discard candidate state |

Partial success is allowed. Valid fields may be adopted together while insufficient fields remain unchanged.

## 17. Security and Privacy

1. Every AI request uses existing Firebase bearer authentication and `requireMember(confId)`.
2. Any approved member who can edit the conference report may manage its Session transcripts and invoke generation; public viewers cannot.
3. Storage rules scope transcript access to approved members of the path's conference.
4. The server loads template, focus, report, Session, and transcript path from trusted storage.
5. The DeepSeek API key never reaches the browser.
6. Raw transcript text, Evidence, and user focus are excluded from public report HTML, exports, and application logs.
7. Logs may contain request IDs, durations, error codes, and counts, but never source text or generated private content.
8. Transcript content is treated as untrusted data to resist prompt injection.
9. User instructions may adjust emphasis and style but may not disable evidence rules.

## 18. Testing

### 18.1 Deterministic unit tests

- TXT/Markdown paragraph segmentation and source positions.
- SRT/VTT cue parsing, timestamps, and malformed input.
- Empty, unsupported, oversized, and invalid-encoding input.
- Evidence ID existence and exact-quote matching.
- Template-field selection, source policy, type, length, and item constraints.
- Current user's conference focus selection without cross-user aggregation.
- Candidate field and transcript hash comparison.
- Transcript prompt-injection text remaining inert data.

### 18.2 API tests with mocked DeepSeek

- Approved membership is required.
- Session requests perform Evidence then Writing calls.
- Daily requests perform only a Writing call.
- Template, report, focus, and transcript are loaded server-side.
- Empty/invalid JSON and transient failures retry once.
- Invalid Evidence is removed.
- Insufficient fields remain untouched.
- No candidate generation path writes Firestore.

### 18.3 UI tests

- Paste and `.txt/.md/.srt/.vtt` upload.
- Safe transcript replacement and deletion.
- Mode and optional instruction request payloads.
- Focus display in the generation dialog.
- Candidate and expandable Evidence rendering.
- Cancel leaves fields unchanged.
- Adoption writes only successful fields.
- Stale hashes block adoption.

### 18.4 End-to-end scenarios

1. Set a personal conference focus, add a Session from My Sessions, upload VTT, generate, inspect timestamp evidence, and adopt.
2. Search the full calendar, add a non-assigned Session, paste text, and generate.
3. Improve an existing manual draft and verify it is included in context.
4. Append missing points without duplicating current content.
5. Generate a daily core-points field from current report content.
6. Verify photographs, fixed fields, transcripts, focus, and Evidence never enter public output.
7. Replace a transcript or modify a field during generation and verify adoption is blocked.

## 19. AI Quality Evaluation and Acceptance Criteria

Maintain a small set of 8–12 fixed transcript fixtures covering short and long text, all four formats, mixed input languages, names and numbers, repeated or contradictory speech, insufficient material, prompt injection, and focus-relevant versus irrelevant content.

Acceptance criteria:

- 100% of generated factual claims reference valid Evidence.
- 100% of displayed quotes can be found in the referenced source.
- 100% of model responses accepted by the server conform to the bound template schema.
- AI never modifies formal report content before explicit adoption.
- Human review finds at least 95% of factual statements supported by their cited source.
- Unsupported content is withheld rather than invented to fill a template.
- Transcript, focus, and Evidence never enter public output or logs.
- Initial latency is measured during real use but does not justify a queue or monitoring system until synchronous requests demonstrate a real problem.

## 20. Components and Boundaries

The feature should remain divided into focused units without becoming a framework:

- **Transcript control:** upload, paste, view, replace, delete.
- **AI generate button/dialog:** collect mode and optional instruction.
- **Candidate modal:** render template fields and Evidence, then adopt or discard.
- **AI API route:** authenticate, load authoritative context, orchestrate model calls, and return a candidate.
- **Transcript parser:** deterministic format parsing and source locations.
- **DeepSeek client:** one provider-specific server wrapper using JSON output.
- **Validators:** minimal template-shape, source-reference, and quote validation.

Do not introduce a generic agent framework, workflow engine, vector store, or provider abstraction in the MVP.

## 21. LLM Wiki Influence

`nashsu/llm_wiki` is an architecture reference only. ConferenceFlow adopts these ideas:

- immutable raw sources;
- a purpose-like direction, represented here by per-conference user focus;
- analysis before generation;
- human review before publishing generated content.

ConferenceFlow does not embed, copy, or run the LLM Wiki desktop service. Its Tauri/Rust/local-filesystem architecture, persistent Wiki, graph, retrieval system, and GPLv3 code are not dependencies of this feature.
